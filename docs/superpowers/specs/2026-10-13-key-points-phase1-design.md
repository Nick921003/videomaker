# 重點清單（第一期）設計

日期：2026-10-13
狀態：待使用者審閱
範圍：第一期 = 重點清單 + 講義型簡報 + 概念樹心智圖。影片、元件選擇、旁白改寫屬第二期，另立規格。

## 1. 為什麼要做

三種成品目前共用「共同教學規劃」（`studio/teaching_plan.py`）。它其實是一份**影片腳本**：7 段場景，每段有提問、旁白式講解、畫面類型。簡報與心智圖從這份腳本硬轉，結果：

- 簡報把影片的逐步浮現拆成多頁，16 頁中第 1–4、7–12 頁標題相同，看起來像影片截圖。
- 心智圖的葉節點是旁白整句，並且同一意思重複出現在多個節點。
- 重點照「影片怎麼講順」排，不是照「學生該學到什麼」排。以 C 迴圈教材為例，教材主軸是三要素與差一、無窮迴圈兩個坑，規劃卻把附帶說明「走讀時分四步」拉成開場重點，結尾的「閱讀檢查」則是教材裡沒有的。

病根是中間層帶了影片的形狀。第一期把中間層換成**與形式無關的重點清單**，各形式自己轉換。

## 2. 已定案的決定

| 項目 | 決定 |
| --- | --- |
| 教材對象 | 學生自學用的多元教材，不是老師上課用 |
| 重點從哪來 | 照教材自己的結構決定**有哪些重點**，再用學習目標檢查有沒有偏題 |
| 重點怎麼講 | **不照本宣科。** 每個重點從學生的一個具體疑問出發，只回答這個問題；與回答無關的細節，教材有寫也不放 |
| 教材來源 | 有結構的 Markdown（BridgeAI 知識點格式）直接用；PDF／PPT 由 AI 推論結構，標成「推論」，確認後才可製作 |
| 簡報 | 講義型：一頁一個重點，不聽旁白也能讀懂 |
| 心智圖 | 概念樹，節點只放短詞，點開才看說明與出處 |
| 擴充 | 未來會加測驗、閃卡等產出形式；重點清單第一期就抽出「常見錯誤」供日後使用 |

### 「從學生疑問出發」的例子

教材講 for 迴圈。學生真正會卡的可能是「for 後面括號裡為什麼用分號隔成三段？」，那這個重點就從這一點切入：三段各管什麼，漏了哪一段會怎樣。它不必依序把迴圈的語法、流程、範例全部搬過來。

同理，一份講蘋果樹生長的教材，重點可以是「蘋果在什麼情況下才會結果」，不需要把發芽、施肥、日照全部講一遍。

## 3. 架構

```
教材 ──→ 重點清單 key_points.json ──┬──→ 講義型簡報（純轉換，不呼叫 AI）
        （每單元呼叫一次 Gemini）     ├──→ 概念樹心智圖（純轉換，不呼叫 AI）
                                      └──→〔第二期〕影片、〔以後〕測驗／閃卡
```

- 只有抽取重點清單會呼叫 AI。轉換器是純函式：同一份重點清單轉兩次，輸出逐位元組相同。
- 舊的共同教學規劃**保留不刪**。第二期改好影片前，影片照舊使用它。
- 簡報與心智圖用新的 `--quality keypoints` 模式接入既有 runner（`workbench/run_slides.py`、`workbench/run_mindmap.py`），並設為預設；舊的 `professional` 模式保留，供新舊對照與回退。

### 新增模組

| 模組 | 職責 | 依賴 |
| --- | --- | --- |
| `studio/key_points.py` | 提示詞、JSON schema、`build_key_points(material, complete_json, source_context)`、`validate_key_points(kp, material)` | 只依賴教材資料與注入的 `complete_json` |
| `studio/handout.py` | `key_points → deck`（講義版型）。純函式 | `key_points` 契約 |
| `studio/concept_tree.py` | `key_points → mindmap`（概念樹）。純函式 | `key_points` 契約 |
| `workbench/key_points.py` | 快取、鎖、版本綁定、待確認狀態。仿 `workbench/teaching.py` 既有寫法 | 上述 studio 模組 |

既有模組要配合修改：

- `studio/deck_contracts.py`：新增 `handout` 版型。
- `studio/pptx_export.py`：畫 `handout` 版型。
- `studio/mindmap.py`：節點加選填欄位 `detail`、`sources`，契約版本號遞增，舊版仍可讀。

## 4. 重點清單契約 `key_points.json`（contract_version 1.0）

### 單元層

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `contract_version` | `"1.0"` | |
| `content_version` | str | 綁定教材版本；教材一改，清單即失效 |
| `title` | str | 單元名稱 |
| `structure` | `"material"` \| `"inferred"` | 結構是教材寫的，還是 AI 推論的 |
| `status` | `"ready"` \| `"needs_review"` | `inferred` 一律從 `needs_review` 開始 |
| `objectives` | list | `{id, text, inferred: bool, sources}` |
| `points` | list | 3–8 個重點，順序即概念樹的前序走訪順序 |

### 每個重點

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `id` | str | 單元內唯一 |
| `title` | str | **≤ 12 字**短詞，直接當心智圖節點 |
| `question` | str | 學生會實際問出口的疑問，必須指向教材裡的具體東西（某段程式、某個符號、某個現象），不得是「什麼是 X？」這類泛問 |
| `type` | enum | `concept` 觀念 / `process` 過程 / `compare` 比較 / `mistake` 錯誤示範 / `code_trace` 程式走讀 / `data` 數據。第一期只儲存，第二期用來篩元件候選 |
| `objectives` | list[str] | 對應的學習目標 id；空陣列代表「補充」 |
| `explanation` | str | 只回答 `question`；不聽旁白也讀得懂；**上限 150 字** |
| `example` | object \| null | `{kind: "code" \| "formula" \| "text", content, language?}` |
| `misconceptions` | list | `{wrong, why, correct}`，可為空；日後出測驗用 |
| `parent_id` | str \| null | 上層重點 id；null 表示第一層 |
| `sources` | list | `{section_id, quote}`，quote 必須逐字存在於教材 |

**禁止欄位**：任何畫面、版型、頁數、時長、旁白、元件名稱。驗證器遇到未知欄位一律拒絕。

### 150 字上限怎麼定

先以 150 字為上限，用第 9 節的四份教材試跑校準：若合格的講解普遍遠低於上限，或使用者認為 150 字講不清楚，就依試跑結果調整。調整後的數字寫回本文件。**超過上限一律視為抽取不合格並退回濃縮，不拆頁。**

## 5. 自動檢查（`validate_key_points`）

以下任何一條不過，就是抽取不合格：

1. 每條學習目標至少被一個重點的 `objectives` 引用。
2. 每條 `sources.quote` 能在對應 section 的原文中逐字找到（比對前統一全形與半形、空白）。
3. `title` ≤ 12 字；`explanation` ≤ 上限；`question` 非空，且不是「什麼是…」開頭的泛問。
4. `parent_id` 必須指向已存在的重點；不得自連、不得形成循環。
5. 重點數量在 3–8 之間；`id` 不重複。
6. 不含任何禁止欄位。

`objectives` 為空的重點不算錯誤，會在對照表上標「補充」讓使用者判斷。

## 6. 轉換器

### 講義型簡報 `studio/handout.py`

- **頁序**：封面（單元名稱、學習目標）→ 每個重點一頁，照 `points` 順序 → 「常見錯誤整理」頁（只在至少一個重點有 `misconceptions` 時產生）。
- **重點頁**：標題用 `question`，副標用 `title`；接著是 `explanation` 全文、`example` 區（程式用等寬字型）、本重點的常見錯誤框（錯的寫法 → 為什麼錯 → 正確寫法）；頁腳列教材出處。
- **常見錯誤整理頁**：彙整所有 `misconceptions`，每條標出來自哪個重點。
- **容量**：在既有最低可讀字級內縮放；仍放不下就明確報錯，指出是哪個重點的哪個欄位。照第 4 節的上限，這種情況應該極少發生；一旦發生，代表上限或版型需要調整，不是要拆頁。
- **輸出**：既有 deck 契約加上新的 `handout` 版型，經 `export_pptx` 輸出原生可編輯物件，不是圖片。

### 概念樹心智圖 `studio/concept_tree.py`

- **結構**：根節點為單元名稱；`parent_id` 為 null 的重點掛在根下，其餘依 `parent_id` 往下長。
- **節點文字**：只顯示 `title`。
- **點開**：`explanation` 的前兩句、`sources` 原文，以及「看講義第 N 頁」（N 由講義頁序決定）。
- **畫法**：沿用既有 `render_mindmap_svg` 的可展開版本，只換資料來源。

## 7. 教材來源與待確認流程

- **有結構的 Markdown**：沿用現有教材讀取流程。抽取時把教材標題（學習目標、核心觀念、常見錯誤……）當作結構提示；`structure = "material"`，`status = "ready"`。
- **PDF／PPT**：沿用現有讀取與整理流程（`workbench/run_normalize.py`、`studio/material_normalizer.py`），其輸出是逐頁文字。抽取時由 AI 推論學習目標與重點；`structure = "inferred"`，`status = "needs_review"`，推論出的目標標 `inferred: true`。
- **確認介面**（第一期最小可用版）：
	- 單元頁上方顯示提示「這份教材的學習目標是 AI 推論的，請確認」，展開後是對照表（左為教材段落標題，右為重點、疑問與對應目標）。
	- 「確認」按鈕：把 `status` 改為 `ready`。
	- 「重新抽取」按鈕：可附一句話，例如「重點應放在 IPO 的三個部分」。這句話會帶進下一次抽取的提示詞。
	- 第一期**不做**逐條編輯。
- **擋製作**：`status ≠ ready` 時，簡報與心智圖的製作按鈕停用；API 與 runner 也會直接拒絕，不只在介面上擋。

## 8. 失敗處理

- **抽取不合格**：把未通過的條目原樣回傳給 AI 修正，最多重試 2 次（加上首次共 3 次呼叫）。仍不合格就停止，失敗的候選另存到 `key_points_attempts/`（仿 `teaching_plan_attempts/`），介面用白話列出哪一條沒過。**不得放寬檢查放行。**
- **講義放不下**：見第 6 節，明確報錯，不越界、不拆頁。
- **教材改版**：`content_version` 不符即視為失效，需要重新抽取；沿用 `generation_material` 的版本機制。抽取期間教材若改變，拒絕發佈。
- **費用**：沿用 `guard_budget` 預算上限與 `usage.jsonl` 紀錄；重試的費用照實計入。

## 9. 驗證與過關標準

### 測試教材（`C:\Users\pjw92\Desktop\計概課程資料`）

| 教材 | 用途 |
| --- | --- |
| `for 迴圈.md` | 過程型、程式走讀多 |
| `多分支決策：else if 與 switch.md` | 比較型多 |
| `AI 協作與單位換算實作.md` | 即 q4 教材，與舊規劃做新舊並排 |
| `邏輯先行與 IPO 模型.pdf` | 測推論與待確認流程 |

### 自動測試（不花錢）

- `validate_key_points` 的每一條規則都有正向與反向測試。反向測試要證明「壞輸入一定被擋」，避免檢查本身失效卻顯示通過。
- 轉換器的決定性：同一輸入轉兩次，PPTX 與 SVG 逐位元組相同。
- 講義不越界：實際讀取產出 PPTX 中各文字框的位置與大小並斷言，不比對算式。
- 待確認狀態下，API 與 runner 確實拒絕製作。

### 實跑（付費，只呼叫 Gemini，不配音、不出片）

四份教材各跑一次。交給使用者的東西：

1. 每份一張對照表（左為教材段落標題，右為重點、疑問、對應目標、是否補充）。
2. 講義 PPTX 與心智圖 SVG。
3. q4 的新舊並排。
4. 實際費用。

### 過關標準

- 自動檢查全數通過。
- 四份中，使用者判定「重點抓對」的至少 3 份。
- 不合格的那份，要能指出錯在哪一步：教材讀取、重點抽取，或轉換。
