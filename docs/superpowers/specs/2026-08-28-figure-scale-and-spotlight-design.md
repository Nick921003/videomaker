# 示意圖填滿區域 ＋ 真正的聚光燈 — 設計文件

**日期**：2026-08-28
**來源**：使用者看完三支對照影片後的兩個回報。

---

## A. 示意圖永遠是那麼小

### A.1 實測

同一份教材、三種模式下 `boxes` 單項的實際尺寸：

| 頁 | 內容 | 置中（可用寬 1760） | 雙欄（可用寬 810） | 自動（1680） |
| --- | --- | --- | --- | --- |
| p2 | `boxes` 3 項 | **360×104** | **360×104** | **360×104** |
| p1 | `compare` | 850×62 | 375×62 | 810×62 |

`boxes`／`steps` **三種模式一模一樣**，給它 1760px 也只畫 360px。

### A.2 原因

`render_slides.py` 第 136 行把每格寬度寫死上限，高度用常數：

```python
w = min(360, region["w"])
total = FIG_ROW_H * n + gap * (n - 1)      # FIG_ROW_H = 104，常數
```

`compare` 的寬度會跟著區域縮放，但列高 `74` 同樣寫死（`layout.py:107`）。

**結果**：圖永遠填不滿拿到的區域，區域越大空白越多。這是這輪版型改造的直接缺口——我把區域切大了，卻沒讓圖跟著長。

### A.3 要改成什麼

尺寸**由區域推導**，不是常數：

- `boxes`／`steps` 橫排：格寬 = `(region_w - 間距總和) // n`，上限拉高到不會醜的程度（建議 520，不是 360）；格高隨區域高度按比例放大，上限同樣拉高。
- `boxes`／`steps` 直排：格寬吃滿欄寬（扣內距），格高隨可用高度分配。
- `compare`：面板寬已經會縮放，**列高改成隨可用高度分配**（現行 74 當下限）。
- 字級跟著 `fit_font` 自然放大（現行起始值 30／26 是上限，區域變大時應該提高起始值）。

### A.4 這件事有陷阱

**`layout.fig_height()` 與 `render_slides.draw_figure()` 必須算出同一個高度。** 這兩處各算一份、其中一份漏了東西，正是這個專案已經被咬過兩次的形狀（C2 的 caption、`fig_height` 的直排高度）。任何改動都要兩邊同步，並且要有測試把它們釘在一起。

## B. 「聚光燈」其實是螢光筆

### B.1 實測

抽 11 個時間點量整張影格的平均亮度，兩支影片全程都是 238–240，**沒有任何壓暗的低谷**。真的有聚光燈的話那條線會明顯下陷。

### B.2 原因

`render_video.py` 的分派：

```python
for eff in active([... if e["type"] == "spotlight"], t):
    if eff.get("style") == "code":
        frame = apply_code_focus(...)
    else:
        frame = apply_highlight(frame, eff, t, hl_rgb)   # ← 螢光筆，不是聚光燈
```

`spotlight` 型別實際走 `apply_highlight`，在目標框刷一層 `#F2D9A0` 底色。`theme.effects.dim`（`#2A231C`）與 `compile_timeline.py:116` 算好的 `eff["dim"] = 0.62` **只有程式碼頁走得到**，一般元素算了沒人用。

**為什麼雙欄看起來沒有**：螢光筆寬度就是目標框寬度。同一個 `p1_fig:l1` 在置中是 **882×94**、在雙欄是 **407×94**——面板壓成一半，螢光筆跟著剩一半，在 1920 寬的畫面上淡到看不出來。

### B.3 要改成什麼

**聚光燈 = 壓暗周圍 ＋ 鏡頭推近目標。**

1. 新增 `apply_spotlight`：把目標框**以外**的區域按 `eff["dim"]` 壓暗，框內維持原亮度。現有的螢光筆刷色保留（它標示目標很有效），兩者疊加。
2. **自動配一個鏡頭推近**：`zoom()` 早就存在（`render_video.py`，用 LANCZOS 所以推近中文字不糊），但只有 LLM 主動下 `camera` 動作時才會動——實測這支片五張圖頁**零個鏡頭動作**。改成 `compile_timeline` 在編譯每個 spotlight 時自動配一個推近。

### B.4 推近的節制

不是每個 spotlight 都該推近，整片一直縮放會暈：

- 目標**佔畫面比例夠大**（建議 ≥ 8%）就不推——本來就看得清楚。
- 推近幅度隨目標大小反向調整，**上限 1.4 倍**。目標越小推越多。
- 推近的中心是目標框的中心，且畫面不得推出畫布外（`zoom()` 已經有夾制）。
- 同一頁連續兩個 spotlight 之間要有鏡頭過渡，不能瞬移。

### B.5 強調必須落在「正在講的那一項」，不是整張圖

使用者回報：有時候強調某一句時，螢光筆刷的是**整張示意圖**，而不是正在講到的那一項。

我試著從編譯結果重現但**做不出來**——p2 編出來的效果全是單項（`p2_fig:i1`／`i2`／`i3`，各 392×136），沒有任何指向整張 `p2_fig` 的效果（那會是 392×396）。成因未確認，但要求本身是對的，所以直接擋在編譯層：

1. **`compile_timeline` 遇到指向「有子項的 figure 整體」的 `spotlight`／`laser` 時，要當成編排缺陷回報**（`WARN` 等級診斷，訊息要指出該用哪些子代號）。整張圖被刷起來對觀眾沒有指示作用——等於沒強調。
2. 例外：`reveal` 與 `camera` **可以**指向整張圖（讓整塊浮現、把鏡頭帶到整塊，都是合理的）。這條只管強調類效果。
3. 加一則測試：把一個指向整張 figure 的 `spotlight` 動作丟進編譯器，必須出現那則診斷。

順帶：這也解釋了為什麼「強調」在雙欄裡特別難看見——目標框越大，刷色越沒有指示性；目標框太小，刷色又太淡。B.3 的壓暗＋推近能同時解決兩端。

## C. 硬性約束

沿用 `CLAUDE.md` 全部不變量，另加：

1. **`layout.fig_height()` 與 `draw_figure()` 算出的高度必須一致**，並有測試釘住（見 A.4）。
2. **`layout.py` 仍須零 import、無副作用。**
3. **所有可定址代號照舊全數輸出**：`{id}`、`{id}:L{n}`、`{id}:i{n}`、`{id}:l{n}`、`{id}:r{n}`、`{id}:caption`。
4. **任何模式、任何 prompt 契約內的輸入都不得溢出所屬區域。** 圖變大之後容量守門更容易觸發，降級行為必須仍然正確。
5. **決定性**：同教材同模式同種子，重跑逐位元組相同。
6. **配色只從 theme 取**，不得寫死顏色。

## D. 驗證

| 項目 | 方法 |
| --- | --- |
| 圖真的變大 | 同一頁在 1760／810 兩種區域寬下的單項尺寸**必須不同**，且都比 360 大 |
| 兩處高度一致 | 對每種 kind × 項目數 × 區域寬的組合，`fig_height()` 的預測必須等於 `draw_figure()` 實際畫出的 `boxes[eid]["h"]` |
| 零溢出 | 五份教材 × 四種模式，每個框都在所屬區域與畫布內 |
| **聚光燈真的壓暗** | 渲染一支片，抽樣整張影格平均亮度，聚光期間必須出現 **≥ 15% 的低谷**。目前是 0%——這條就是抓出這個 bug 的那個量測 |
| 鏡頭有動 | 編譯後每頁的 `camera` 數量必須大於 0（目前圖頁是 0） |
| 決定性 | 同輸入重跑逐位元組相同 |
| 視覺 | 產出對照影片交使用者確認，**不自行判定好壞** |

## E. 實作後的三處修正（2026-08-28）

規格與實作對不上的地方，以這節為準。

### E.1 圖是「適度變大」，不是填滿

A.3 的初版寫成「直排吃滿欄寬（扣 40px 內距）」，實作照做，810px 的欄位長成 770px——**四周一點留白都不剩，看起來是撐爆不是變大**。使用者當場否決。

改成橫排直排一律吃同一個上限 `FIG_MAX_BOX_W = 520`（舊值 360）。實測：

| 區域寬 | 舊 | 填滿版 | 現行 |
| --- | --- | --- | --- |
| 810（半欄） | 360 | 770 | **520** |
| 1760（滿版，3 項） | 360 | — | **520** |
| 1760（滿版，4 項） | 360 | — | **420** |

### E.2 壓暗只給程式區塊

B.3 寫成「所有 spotlight 都壓暗」，實作照做，於是**襯一個標題也要把整頁壓黑**。使用者回報後改成：只有 `style == "code"` 的 spotlight 走壓暗，其餘一律螢光筆。

實作過程中另外發現一個死碼：判斷曾寫成「`target` 結尾是 `_code` 就壓暗」，但 `compile_timeline` 產生的 `style` 欄位一律是 `"code"`／`"text"`，那條分支**永遠走不到**。已改用 `style`。

保留區也從「效果自己的框」改成「整張 `CODE_BOX`」——壓暗負責把注意力帶到程式碼卡，卡內哪幾行由既有的 `apply_code_focus` 處理。判斷抽成純函式 `render_video.spot_style(eff)` 以便單獨測試。

實測（整頁平均亮度，240 ≈ 未壓暗）：

```
秒     90     100    108    115    122    130
頁     p3圖   p4碼   p4碼   p4碼   p4碼   p5圖
亮度   235    201    196    202    173    236
```

### E.3 鏡頭推近也只給程式區塊，且一對一

B.4 沒限定範圍，實作對每個 spotlight 都配推近，結果：

- 幾乎每一格都在做 LANCZOS 全幅縮放，**渲染時間從約 95 秒變成 402 秒**，畫面上看不出好處。
- 更糟的是自動配對讓位給 LLM 的顯式 `camera` 動作（條件是「同一時刻沒有顯式 camera 才配」）。LLM 沒有幾何概念，實測 p4 四個聚光燈裡有兩個配到 `target=None` 的**拉遠**鏡頭——聚光燈亮起的同時鏡頭往後退。使用者的原話是「很奇怪，要以剪輯師的視角看」。

改成：推近只在 `is_code` 時自動配，且**同一時刻以自動配的為準**（顯式 camera 讓位）。渲染時間回到 **149 秒**。

### E.4 驗證方式的修正

跑重渲時 `--from slides --until video` 會把 `actions`（付費 LLM）包在區間內。正確作法是分兩段：

```bash
.venv/bin/python video_engine/run.py <教材> --from slides --until slides
.venv/bin/python video_engine/run.py <教材> --from storyboard --until video
```

跑完用 `md5sum` 確認 `examples/<id>.actions.json` 未被動到。
