# 動態規格：這支引擎怎麼決定「動起來好不好看」

畫面做得出來是 `render_video.py` 的事，動起來好不好看是這份文件的事。
所有數值都有來源，不是憑感覺調的——改之前先看它為什麼是這個值。

## 來源

| 來源 | 授權 | 我們用了什麼 |
| :--- | :--- | :--- |
| [LottieFiles motion-design-skill](https://github.com/LottieFiles/motion-design-skill) | MIT | 緩動曲線、時長分級表、依序進場間隔、過衝預算 |
| [Video Shotcraft](https://github.com/Vincentwei1021/video-shotcraft) 鏡頭配方卡 | Apache-2.0 | 馬克筆底線、掃描線的參數與已知坑 |
| `docs/agy_results/2026-08-24-video-effect-vocabulary.md` | 本專案 | 既有六個效果的存廢判定、退場淡出時長 |

兩個專案都是 JS／React 生態，**程式碼一行都沒有搬**——搬的是參數與判準。

## 三條緩動曲線，不可互換

混用是「動起來很機械」最主要的來源。

| 用途 | 曲線 | cubic-bezier | 為什麼 |
| :--- | :--- | :--- | :--- |
| 進場 | `ease_enter` | (0.05, 0.7, 0.1, 1) | 一開始就衝出去，尾巴慢慢收——東西「到了」比「怎麼來的」重要 |
| 退場 | `ease_exit` | (0.3, 0, 1, 1) | 慢慢起步再加速離開，觀眾不會覺得東西被抽走 |
| 畫面內位移 | `ease_move` | (0.2, 0, 0, 1) | 鏡頭推近、換頁交叉淡化，兩頭都要穩 |

## 時長

進場時長依元素大小分級（`compile_timeline.py`）。全部同一個時長，畫面會很機械。

| 元素 | 佔畫面 | 時長 |
| :--- | :--- | :--- |
| 條列項 | < 2% | 260 ms |
| 卡片、示意圖方塊 | < 10% | 320 ms |
| 標題、整張圖 | ≥ 10% | 420 ms |

**退場一律是進場的 70%**（`EXIT_RATIO`）。退場比進場快是通則——
東西離開時觀眾已經看完了，慢慢消失只是拖時間。

其餘固定值：螢光筆刷過 380 ms、程式碼壓暗淡入 420 ms、底線畫出 330 ms、
換頁交叉淡化 420 ms、鏡頭推近 600 ms。

## 起點排開（`settle_starts`）

動作只寫語意代號、不寫時間碼，所以「什麼時候動」全部落在編譯期解決——
跟座標一樣。有兩件事 LLM 無從避免，只能在這裡處理：

1. **非阻塞動作連著寫會全部落在同一毫秒**。一起蹦出來讀成一整塊
2. **每頁第一個動作必然落在頁首**，撞上換頁交叉淡化，殘影蓋在上面等於白做

`settle_starts()` 把同一刻的動態依原始動作順序排開：

| 相鄰兩個動態 | 間距 |
| :--- | :--- |
| reveal → reveal | 60 ms |
| 其他任意組合 | 80 ms（`MIN_GAP_MS`，再近就讀成同時發生） |

頁首的動態一律等到 `TRANS_MS`（420 ms）之後才起動。每組總延後量壓在
400 ms 內，不然視覺會落後講稿太多。

### 為什麼是自動排開，不是警告

第一版寫成 lint，一支片噴 14 條警告——因為這是引擎的**設計實情**不是偶發錯誤，
而排開這件事不需要任何判斷，規則是死的。會警告一個作者改不動的東西，
等於把成本丟給人。lint 只留 `settle_starts` 排不掉的：
效果活太短（那段講稿就是那麼短，只能回頭改講稿），加兩條安全網防止
`settle_starts` 哪天被改壞。

## 過衝

| 對象 | 過衝 | 說明 |
| :--- | :--- | :--- |
| `reveal` 位移 | 5% | 紙感材質上限。30 px 位移換算只有 1.5 px，是落地的軟度不是彈跳 |
| 鏡頭推近 | 2% | 推到定位再回穩，像真的攝影機。這個看得出來 |

教學內容的調性偏穩重，不用彈性材質那種 15–25% 的彈跳。
係數 `c1` 由 `back_c1()` 二分法解出來，峰值 = 4c1³ / (27(c1+1)²)，沒有解析解。

## 效果語彙

| 效果 | 判定 | 說明 |
| :--- | :--- | :--- |
| 螢光筆 | 核心 | 正片疊底刷過文字重點，不壓暗其他內容 |
| 程式碼區域壓暗 | 核心 | 只壓程式碼卡片，目標行保持原亮度，左側加範圍括號 |
| 左移淡入 | 核心 | 漸進揭露，30 px 位移＋依序錯開 |
| 鏡頭推近 | 保留，節制用 | 每頁最多兩次。用 LANCZOS 重取樣，中文字與等寬碼才不會糊 |
| 馬克筆底線 | 改造後保留 | 見下 |
| 掃描線 | 新增 | 見下 |
| Ken Burns 全頁緩慢縮放 | **已移除** | 連續次像素縮放讓中文字型與等寬碼持續重取樣發糊，沒有任何教學效益 |

### 馬克筆底線（改造）

原本是等寬線條加一顆筆尖圓點，圓點是純裝飾雜訊，已拿掉。現在：

* 330 ms 畫完（約 10 格 @30fps）。慢過 14 格會讀成進度條
* 中段最寬、首尾 0.6 倍。等寬會讀成機器畫的線
* 邊緣輕微噪聲＝手繪筆觸。太糙會讀成故障
* 貼著文字底部（用 `pad` 反推字底位置）。離遠了會讀成分隔線

### 掃描線（新增）

一道光等速由上往下掃過整塊程式碼一趟，帶漸層拖尾，宣告「開始逐行讀這段程式碼」。

* **等速是命門**——加了緩動會讀成「有人在拖進度條」，而不是「機器在讀」
* 只掃程式碼區塊內，漏出去就變成掃整個畫面
* **每頁只掃第一次**（`mark_first_scan`）。每次聚焦都掃就退化成裝飾
* 程式碼本身全程靜止，只有光在動。文件也跟著動的話，觀眾分不清是「被讀」還是「在載入」
* **等換頁交叉淡化走完（450 ms）才起掃**。跟換頁疊在一起的話，殘影還在，等於白掃

## 節奏閘（`validate.py`）

一段語音配一個視覺重點。同時動太多處，觀眾眼睛來不及跟。

| 檢查 | 提醒 | 錯誤 |
| :--- | :--- | :--- |
| 兩段 speech 之間的 spotlight／laser／camera | > 2 | > 4 |
| 一口氣連續 reveal | > 5 | — |
| 每頁鏡頭推近 | — | > 2 |

## 時序 lint（`compile_timeline.py`）

編排閘管語意，時序 lint 管時間軸，兩者抓的是不同的洞。

| 檢查 | 級別 | 說明 |
| :--- | :--- | :--- |
| 效果活得比「進場＋退場」還短 | 提醒 | 畫不完就開始淡出，畫面會抽動。要回頭把那段講稿講長一點 |
| 動態起點落在換頁淡化窗內 | 錯誤 | `settle_starts` 應該排掉了，會叫代表它被改壞 |
| 相鄰動態起點間距不足 | 錯誤 | 同上，安全網 |

所有時序常數集中在 `video_engine/motion.py`——渲染器照它畫、編譯器照它檢查。
兩邊各寫一份的話，改了一邊忘了另一邊，lint 會拿錯的基準去檢查對的畫面。

改 prompt 不如改閘——模型會被打回重做，改 prompt 只是建議。
