# VS Code 中 printf 不輸出：Windows 實測紀錄

日期：2026-10-22。環境：Windows、VS Code、MSYS2 UCRT64 gcc（`C:\msys64\ucrt64\bin`）、gdb 18.1、C/C++ 擴充 1.34.4、Code Runner 0.12.2。測試資料夾：`C:\Users\pjw92\vscode_printf_probe`（使用者在 VS Code 實際點按，結果由程式自記錄＋截圖）。

這份紀錄是影片內容的依據：影片演出的每一幕都要對得上這裡的實測結果。

## 底層規則（UCRT stdout 緩衝）

| stdout 接到 | 實測 | 方法 |
|---|---|---|
| 終端機（FILE_TYPE_CHAR） | 沒換行的 printf 印完立刻出現，不需 fflush | `probe.c` 讀回自己的終端機畫面，附陽性對照 |
| 管線（FILE_TYPE_PIPE） | 全緩衝：有換行的字也不送出，只有 fflush 或程式結束才送出 | `timing.c`：第 0 秒印的「A有換行」到第 2.1 秒（fflush）才抵達 |

AGY 研究報告寫「終端機下要換行才 flush」，與實測不符（那是 Linux glibc 的行緩衝規則）。

## VS Code 各執行方式

| 執行方式 | stdout | 現象 |
|---|---|---|
| Code Runner 預設（輸出面板） | 管線 | `s1_scanf.c`：提示字不出現、程式卡住；`s3_slow.c`：每行都有 `\n` 仍不顯示；輸出面板無法把輸入送進程式 |
| Code Runner 預設＋fflush | 管線 | `s2_scanf_fflush.c`：提示字出現，打字後程式沒收到，仍卡住 |
| Code Runner `runInTerminal: true` | 終端機 | 三支都正常，不需 fflush；`s3_slow.c` 每秒出現一行（使用者確認）；中文亂碼 |
| F5（launch.json internalConsole／integratedTerminal／externalConsole） | 終端機 | 正常、中文正常。即使設 internalConsole，程式仍在「終端機」分頁執行，偵錯主控台只有 gdb 訊息 |
| 右上角 Run C/C++ File | 終端機 | 正常；中文亂碼；工作目錄是 `C:\msys64\ucrt64\bin` |

## 修法

- **Code Runner**：設定「Code-runner: Run In Terminal」打勾（`"code-runner.runInTerminal": true`）。只加 `fflush(stdout)` 不夠：提示字會出現，但 scanf 仍無法輸入。
- F5 與播放鍵本身沒有 printf 問題。

## 順帶發現（學生也會遇到）

1. Windows PATH 沒有 `C:\msys64\ucrt64\bin` 時，用完整路徑呼叫 gcc 會**無訊息失敗**（Code Runner 只顯示 `exited with code=1`）。
2. 終端機（PowerShell）裡 UTF-8 中文輸出會變亂碼；F5 除錯時正常。修法尚未實測。使用者決定另寫一篇短部落格。
3. 播放鍵在 `C:\msys64\ucrt64\bin` 執行程式，讀寫相對路徑的檔案會找錯地方。
4. **PATH 順序會讓 gcc 無訊息失敗**：`C:\iverilog\bin`、`C:\iverilog\gtkwave\bin`（Icarus Verilog）排在 `C:\msys64\ucrt64\bin` 前面時，gcc 的 `cc1.exe` 會載入 iverilog 帶的舊版同名 DLL（libgmp-10、zlib1、libwinpthread-1、libgcc_s_seh-1 等），結果 `exited with code=1`、沒有任何錯誤訊息。把 ucrt64 移到 iverilog 前面就好。iverilog 自己不受影響，因為 Windows 先從程式所在資料夾找 DLL；cc1 不在 bin 資料夾，所以才會去 PATH 找。修過 PATH 後 VS Code 要完全關掉重開（只「重新載入視窗」不會讀到新 PATH）。
5. Code Runner 輸出面板裡 cmd 的中文錯誤訊息（Big5）會顯示成亂碼，例如「'gcc' 不是內部或外部命令」變成一串問號。
6. 設定步驟實測可行：`Ctrl+,` → 搜尋 `run in terminal` → 「Code-runner: Run In Terminal」打勾（使用者層級）。
8. **卡住的程式沒停，下次編譯會 Permission denied**：輸出面板模式下 s1_scanf.exe 等輸入卡住、沒按停止，它一直在背景執行並鎖住 .exe，下一次 `gcc ... -o s1_scanf` 出現 `ld.exe: cannot open output file s1_scanf.exe: Permission denied`。結束那支程式就好。
7. 編輯器右上角的 ▷ 會在 Code Runner 和 C/C++ 擴充套件之間切換，有時收進「⋯」；停止鍵（紅色方塊）只在程式執行中出現。文章只教 `Ctrl+Alt+N` 與 `Ctrl+Alt+M`。

## 尚未證實

- 「以前沒碰到」的原因：可能以前用 F5、或以前勾過 Run In Terminal，需問老師當時的操作方式。

## 中文亂碼（另一篇文章的依據）

`mb.c` 印出中文後讀回自己的終端機畫面比對（實測於真實主控台）：

| 情況 | 終端機 code page | 中文 |
|---|---|---|
| cmd／PowerShell 預設 | 950（Big5） | 亂碼 |
| 先 `chcp 65001` | 65001（UTF-8） | 正確 |
| 編譯加 `-fexec-charset=BIG5` | 950 | 正確，但所有字串都變 Big5（寫進檔案的中文也是），在 UTF-8 終端機（如 F5 除錯）反而亂碼 |

原因：原始檔與 gcc 輸出是 UTF-8，中文版 Windows 終端機預設以 Big5 解讀。F5 除錯正常，因為 C/C++ 擴充的啟動器把終端機設成 UTF-8。
**VS Code 終端機裡 `chcp 65001` 無效**（使用者實測）：chcp 顯示 65001，但執行程式仍亂碼。接上該程式的主控台讀到「輸出 code page=950、輸入=65001」。原因：PowerShell 啟動外部程式前，會依自己記住的 `[Console]::OutputEncoding`（啟動時是 950）重設主控台輸出編碼，chcp 改不到它。一般 conhost 視窗非互動測試時沒重現，VS Code 互動式終端機才出現。
**有效修法**（使用者實測，截圖 `截圖/亂碼/OutputEncoding後正常.png`）：在 PowerShell 執行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`，之後 `.\s1_scanf` 中文正常。
自動套用：`terminal.integrated.profiles.windows` 的 PowerShell args 設為 `-NoExit -Command "[Console]::OutputEncoding = [Text.Encoding]::UTF8; chcp 65001 > $null"`。**學生路徑實測通過**（2026-10-23）：使用者照草稿步驟在「開啟使用者設定 (JSON)」最後一個 `}` 前貼上 profiles＋defaultProfile、存檔、關掉終端機，`Ctrl+Alt+N` 執行 s1_scanf 中文正常；VS Code 新開的 PowerShell 確實帶上 OutputEncoding 參數。縮排混用 Tab／空格不影響。
測試陷阱：程式在等 scanf 時打的 PowerShell 指令會被程式當成輸入吃掉。
